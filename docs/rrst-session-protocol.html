How the RRST paradigm operates the device

Traced from every serial call in the repo — respDeviceHelpers_3-0/*.m, RRS_3-0/code/main.m, and the current device firmware RRST_Teensy_4_version_TMC2209.ino (TMC2209 dual-endstop generation). Three actors: a person doing a one-time mechanical fit, the MATLAB task script, and the Teensy firmware driving the motor.

Updated after the TMC2100→TMC2209 firmware rebuild: re-traced against the actual current firmware and the MATLAB helpers as they exist in this repo today (not the Resp_valve_3-0.ino file the original version of this document cited, which no longer exists in this checkout). Items marked new didn't exist on the firmware generation this document originally described - the task script needed zero changes to benefit from any of them.

Session start
main.m · fixed 65 s wait screen
MATLAB

setupResp() opens the serial port (9600 baud). Unchanged.

MATLAB

calibrateResp() sends a single 'c' byte. main.m then shows a welcome screen for a fixed 65-second countdown (calibrationTime = 65) before continuing - this is a MATLAB-side timer, not something the firmware acknowledges or reports back to.

Worth re-checking on this hardware generation: the current firmware now does a precise fast-approach-then-slow-reapproach homing pass on both endstops (see next step), which is strictly more work per calibration than a single-pass homing sequence. Whether 65 s is still comfortable margin hasn't been timed here - it was never tied to real firmware timing even before.

Firmware

cmd3_Calibrate energizes the driver directly (digitalWrite(EnablePin, LOW)) - no 'e' needed, same practical outcome as before. It homes to the min endstop, then finds the max endstop, latches MaxPosition, and is done - fully automatic, same as always.

New: each endstop is now found twice per calibration - a fast approach, then an automatic back-off and slow re-approach for a more repeatable trigger point - plus auto-correction and hit-counting if the switch misbehaves mid-seek. None of this is visible to the task script; it just takes however long it takes before the next 'c'/'a' gets answered.

Minor quirk worth knowing: calibration energizes the driver but doesn't set the firmware's own "Stepper Enabled" status flag. Anyone watching Live Status or raw 's' output during a running session will see "Stepper Enabled: NO" even while the device is demonstrably calibrated and moving. Cosmetic only - it doesn't affect whether moves actually work.

Staircase picks the stimulus %-obstruction; the two intervals are assigned 0% (s−) and that value (s+), order randomised.

MATLAB

moveResp() to breath 1's position → paced inhale cue → moveResp() to breath 2's position (or moveResp2NoLoad() for the null/sham breath - same underlying 'a'+value call, just targeting position 0) → paced inhale cue.

Firmware

New: every 'a' move now runs through endstop-hit auto-correction - an unexpected switch trigger mid-move is corrected automatically (up to 3 consecutive times) before the device would ever hard-disable. The task gets this reliability improvement with no script changes; it would only ever notice if the safety disable actually tripped.

MATLAB

2IFC + confidence response collected, then moveResp2ITIpos() sends the wedge to a jittered ~50%±30% resting load between trials.

MATLAB

On an invalid or repeated trial, the script's recovery move is another calibrateResp() — a full re-home, not a disable/re-enable cycle.

This same recovery action now also happens to recover from the new endstop-hit safety disable and the new serial-disconnect safety disable below - the task didn't need to be taught about either failure mode to already handle them correctly.

Session end
main.m / experimentEnd.m
MATLAB

One final calibrateResp() re-home, then fclose('all') and window teardown.

Re-traced carefully: fclose('all') only closes raw file identifiers (fopen handles) - the serialport object RD.respDevice is a different kind of handle and is never explicitly closed anywhere in main.m or experimentLauncher.m. In practice the port stays open, held by that variable in the base workspace, until the next experimentLauncher run's own clear all releases it (or MATLAB itself closes). This was already true before the firmware rebuild - not a new finding, just confirmed against the actual current code rather than assumed.

Firmware

No 'd' (disable) is ever sent. As long as the port stays open (see above), the driver's enable pin stays low — the motor is left holding torque, powered, between subjects, same as always.

New: the moment the connection does eventually drop - workspace cleared, MATLAB closed, cable unplugged, a crash - the firmware now notices and auto-disables, invalidating calibration until a fresh 'c'. The old firmware had no such check at all and would have stayed silently "enabled" (electrically) even against a dead connection. This is a pure safety-net addition: it doesn't change the normal between-subjects behavior above, only what happens once the connection genuinely goes away.

What never happens, anywhere in the repo

  • ×
    Disable after use. 'd' exists in the firmware menu but no .m file ever sends it — every writeline call in the repo is 'c' or 'a'<pos>. grep writeline: calibrateResp.m, moveResp.m only
  • ×
    Per-session speed/acceleration tuning. 'f' and 'g' exist for interactive CLI use; the task always runs on whatever's compiled into that firmware build (ACCELERATION 10000, SPEED 16000 - unchanged by the rebuild). RRST_Teensy_4_version_TMC2209.ino
  • ×
    Current/microstep/chopper-mode tuning. The TMC2209 can now do all of this over UART ('i'/'u'/'p'/'t'), unlike the old plain step/dir driver - but the task never sends any of them. It runs on whatever's compiled in (800 mA run / 50% hold / 16 microsteps / SpreadCycle by default).
  • ×
    The new dedicated Retract command. 'y' (cmd22_Retract) jumps straight to the calibrated First-Contact position in one keystroke - added this session, but moveResp2ITIpos/moveResp2NoLoad still compute and send their own 'a'+value instead of using it. Available, not adopted.

Gained for free since the TMC2209 rebuild

  • +
    Mid-move endstop-hit auto-correction. An unexpected switch trigger during any 'a' move self-corrects, up to 3 consecutive times, before a hard safety disable. Previously any unexpected hit was just... whatever the old firmware did with it.
  • +
    Serial-disconnect safety-disable. A dropped connection now auto-disables the driver and invalidates calibration instead of silently staying energized against nothing. The task's existing recalibrate-to-recover pattern already handles this correctly with no changes.
  • +
    Lifetime usage stats, persisted in EEPROM. Every session now silently accumulates into this specific device's lifetime run time, distance traveled, and endstop hit counts - readable later via 's' or the Control Panel app's Live Status, independent of anything the task script does.
  • +
    A live heat-sink temperature reading, if this particular physical unit happens to have the optional DS18B20 sensor installed - auto-detected at boot, no task-side change needed either way.
